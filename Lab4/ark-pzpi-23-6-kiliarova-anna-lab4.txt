1 ЗАВДАННЯ
Метою лабораторної роботи №4 є розробка IoT-клієнта для програмної системи моніторингу свіжості продуктів у холодильнику.
У межах роботи необхідно реалізувати клієнтську частину системи, яка імітує роботу розумного холодильника, забезпечує збір даних з датчиків, їх попередню обробку та передачу телеметричної інформації на серверну частину системи через HTTP API.
Для досягнення поставленої мети необхідно виконати такі завдання:
* обрати та налаштувати середовище емуляції IoT-пристрою;
* реалізувати зчитування даних з датчиків температури, вологості та стану дверцят;
* забезпечити локальну обробку телеметричних даних;
* реалізувати передачу телеметрії на сервер;
* змоделювати поведінку IoT-клієнта за допомогою UML-діаграм;
* виконати тестування взаємодії IoT-клієнта з серверною частиною системи.














2 ОПИС ВИКОНАНОЇ РОБОТИ
2.1. Опис інженерних рішень та архітектури системи
IoT-клієнт розроблено як окремий компонент програмної системи FreshFridge, що функціонує у клієнт–серверній архітектурі.
Клієнт імітує роботу фізичного IoT-пристрою (розумного холодильника) та відповідає за збір телеметричних даних і передачу їх на сервер.
Для емуляції апаратної частини використано онлайн-середовище Wokwi, яке дозволяє моделювати роботу мікроконтролера ESP32 та підключених до нього датчиків без використання реального обладнання.
Як сенсори використано:
* датчик температури та вологості DHT22;
* механічний перемикач, що імітує стан дверцят холодильника.
IoT-клієнт взаємодіє із серверною частиною через REST API. Передача даних здійснюється у форматі JSON з використанням протоколу HTTP. Для захисту доступу до API використовується токенна аутентифікація (JWT), яка передається у заголовку Authorization.
Таким чином, IoT-клієнт є незалежним від серверної реалізації компонентом, що дозволяє масштабувати систему та підключати нові пристрої без зміни основної бізнес-логіки.
2.2. Моделювання поведінки системи
Для аналізу та візуалізації поведінки IoT-клієнта було побудовано UML-діаграми, які дозволяють формально описати сценарії взаємодії та внутрішню логіку роботи клієнта.
На рисунку 2.1 представлено UML-діаграму прецедентів IoT-клієнта, яка відображає основні функції, що виконує пристрій у системі.


  

Рисунок 2.1 – UML-діаграма прецедентів IoT клієнта
        На рисунку 2.2 наведено UML-діаграму діяльності IoT-клієнта, яка деталізує послідовність виконання дій під час роботи пристрою. Діаграма відображає процес ініціалізації пристрою, підключення до мережі Wi-Fi, циклічне зчитування даних з датчиків, локальну обробку даних та передачу телеметрії на сервер. Також показано обробку помилкових ситуацій, зокрема відсутність мережевого з’єднання або некоректні показники сенсорів.

2.4. Програмна реалізація бізнес-логіки
        Бізнес-логіка IoT-клієнта полягає у локальній обробці телеметричних даних перед їх передачею на сервер.
Основним елементом бізнес-логіки є розрахунок інтегрального показника ризику псування продуктів (RiskScore), який враховує температуру, вологість та час відкриття дверцят холодильника.
Фрагмент коду, що реалізує обчислення RiskScore, наведено нижче:
static float computeRiskScore(float t, float h, float doorOpenSecondsInWindow) {
  const float T_MID = 4.0f;
  const float kT = 10.0f;
  float tempPenalty = clampf(fabs(t - T_MID) * kT, 0.0f, 60.0f);


  const float kH = 0.5f;
  float humOut = 0.0f;
  if (h > 70.0f) humOut = h - 70.0f;
  else if (h < 35.0f) humOut = 35.0f - h;
  float humPenalty = clampf(humOut * kH, 0.0f, 25.0f);


  float doorPenalty = clampf(doorOpenSecondsInWindow * 0.05f, 0.0f, 15.0f);


  return clampf(tempPenalty + humPenalty + doorPenalty, 0.0f, 100.0f);
}


Реалізована бізнес-логіка дозволяє виконувати попередній аналіз даних безпосередньо на IoT-пристрої, зменшуючи навантаження на сервер та підвищуючи автономність клієнта.
2.5. Програмна реалізація функцій налаштування
        Функції налаштування IoT-клієнта включають ініціалізацію апаратних компонентів, підключення до мережі Wi-Fi та конфігурацію параметрів взаємодії з сервером.
Фрагмент коду, що відповідає за підключення до мережі Wi-Fi, наведено нижче:
static void wifiConnect() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);


  while (WiFi.status() != WL_CONNECTED) {
    delay(250);
  }
}


Також у коді клієнта визначено параметри серверного API, включно з базовою URL-адресою та токеном доступу, що дозволяє забезпечити захищену передачу телеметричних даних.












































ВИСНОВКИ
        У ході виконання лабораторної роботи №4 було розроблено IoT-клієнт для системи FreshFridge, який імітує роботу розумного холодильника та забезпечує збір, обробку і передачу телеметричних даних на сервер.
Було використано середовище емуляції Wokwi, що дозволило реалізувати та протестувати IoT-клієнт без застосування реального апаратного забезпечення. Реалізована взаємодія з серверною частиною системи підтверджує коректність обраних архітектурних та інженерних рішень.
Отримані результати демонструють можливість подальшого розвитку системи, зокрема розробки клієнтського веб- або мобільного інтерфейсу та розширення функціональності IoT-пристроїв.
