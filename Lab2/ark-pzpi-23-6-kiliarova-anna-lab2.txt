1 ЗАВДАННЯ
     Лабораторна робота №2 має на меті формування вміння студента проєктувати та реалізовувати серверну частину програмної системи на основі реляційної бази даних і прикладного програмного інтерфейсу (API). У межах даної роботи розробка виконується для програмної системи FreshFridge — програмної системи для моніторингу свіжості продуктів у холодильнику.
     У процесі виконання лабораторної роботи необхідно:
- розробити загальну будову серверної частини системи FreshFridge з урахуванням клієнт–серверної архітектури та інтеграції з IoT-модулями холодильника;
- побудувати UML-діаграму прецедентів для серверної частини, яка відображатиме основні сценарії взаємодії користувачів та зовнішніх пристроїв із системою;
- спроєктувати інформаційну модель системи та створити ER-діаграму, що описує основні сутності (користувачі, продукти, категорії, полиці, датчики, показники середовища, сповіщення тощо) та зв’язки між ними;
- на основі логічної моделі даних розробити структуру реляційної бази даних для Microsoft SQL Server, визначивши таблиці, типи полів, ключі, обмеження цілісності та індекси;
- створити діаграму структури БД, яка відображатиме фізичну схему таблиць для системи FreshFridge;
- реалізувати програмну взаємодію серверної частини з базою даних за допомогою Node.js, TypeScript, Express та обраної технології доступу до даних (ORM або інструмент низькорівневого доступу до MSSQL);
- розробити REST API для взаємодії серверної частини з клієнтами (мобільним застосунком, веб-клієнтом та IoT-пристроями холодильника), визначивши основні маршрути для роботи з користувачами, продуктами, показниками датчиків, термінами придатності та сповіщеннями;
- підготувати текстову специфікацію розробленого API із зазначенням призначення ендпойнтів, HTTP-методів, форматів запитів і відповідей, а також вимог до авторизації та валідації даних;
- реалізувати фрагменти програмного коду, що демонструють логіку взаємодії серверної частини з базою даних та клієнтами (контролери, сервіси, модулі роботи з даними).
     Результатом виконання роботи є серверна частина прототипу системи FreshFridge з розробленою базою даних, REST API та специфікацією інтерфейсу, що слугує основою для подальшої реалізації бізнес-логіки та клієнтських застосунків.
 
 
 
 
 
 
 
 
 

2 ОПИС ВИКОНАНОЇ РОБОТИ
     2.1. Опис інженерних рішень та архітектури системи
     Архітектура серверної частини програмної системи FreshFridge побудована на основі клієнт–серверної моделі з підтримкою інтеграції IoT-пристроїв холодильника. Основними вимогами до архітектури є: масштабованість, модульність, надійність роботи з реляційною базою даних та забезпечення безпечної взаємодії між користувачами, програмними клієнтами та сенсорними модулями.
     Для реалізації серверної частини обрано технологічний стек Node.js у поєднанні з TypeScript, що забезпечує статичну типізацію, покращену підтримку рефакторингу та підвищену безпеку обробки даних. Фреймворк Express використовується для побудови REST API завдяки простоті маршрутизації, можливості розширення middleware-компонентами та сумісності з широким набором бібліотек екосистеми Node.js.
     Реляційне сховище даних реалізовано на основі Microsoft SQL Server, який підтримує транзакційну цілісність, складні зв’язки між сутностями та ефективні механізми індексування. Взаємодія серверної частини з БД здійснюється за допомогою ORM або низькорівневого драйвера, що дозволяє формувати параметризовані запити та уникати SQL-ін’єкцій. Такий підхід забезпечує узгодженість логічної моделі даних зі структурою таблиць та полегшує подальше розширення проєкту.
     Архітектура системи FreshFridge передбачає окреме опрацювання таких функціональних доменів:
- Користувачі та автентифікація — модуль, відповідальний за реєстрацію, авторизацію, управління профілем та контроль доступу до даних;
- Продукти та умови зберігання — логіка додавання, редагування, категоризації та відстеження терміну придатності продуктів;
- IoT-модуль холодильника — прийом телеметричних даних про температуру, вологість і стан дверцят та їх подальший аналіз;
- Аналітика та сповіщення — обробка даних сенсорів, визначення ризику псування продуктів, формування попереджень і надсилання push-сповіщень;
- Журнал подій та історія вимірювань — зберігання історичних показників і доступ до них для побудови графіків у клієнтських застосунках.
     Для IoT-комунікації передбачена можливість використання легковагих REST-запитів або MQTT-протоколу у майбутніх розширеннях системи. Накопичені дані сенсорів зберігаються у відповідних таблицях БД, що забезпечує можливість побудови статистики та виявлення аномалій умов зберігання.
     Обрана архітектура забезпечує чітке розділення відповідальностей між модулями серверної частини, полегшує підтримку коду та гарантує узгодженість даних між клієнтськими застосунками і холодильником. Такий підхід створює основу для подальшого масштабування системи та впровадження розширеної бізнес-логіки у наступних етапах розробки.
     2.2. Проєктування бази даних та структури системи
     Для формалізації функціональних вимог до серверної частини програмної системи FreshFridge було розроблено UML-діаграму прецедентів, яка відображає взаємодію користувача, системи та IoT-модуля холодильника. На діаграмі виділено ключові сценарії використання, включно з автентифікацією, керуванням продуктами, переглядом стану холодильника, аналізом показників датчиків, отриманням сповіщень та взаємодією із сенсорним пристроєм. UML-діаграма демонструє логічну структуру системи та її основні функціональні області, що визначають подальшу побудову архітектури (див. рис. 2.1).

Рисунок 2.1 – UML-діаграма прецедентів
     Інформаційну модель системи представлено у вигляді ER-діаграми, яка формує логічну структуру даних і визначає зв’язки між основними сутностями FreshFridge: користувачами, продуктами, категоріями продуктів, полицями холодильника, датчиками, показниками середовища та таблицями сповіщень. ER-діаграма використовується як основа для подальшої розробки фізичної схеми бази даних і дозволяє формалізувати вимоги до зберігання, обробки та інтеграції даних у системі (див. рис. 2.2).

Рисунок 2.2 – ER-діаграма
     На основі логічної моделі даних було створено фізичну структуру реляційної бази даних Microsoft SQL Server. Структура включає таблиці для зберігання інформації про користувачів, продукти, категорії, полиці, телеметричні показники датчиків, історію вимірювань та генеровані системою сповіщення. Для кожної таблиці визначено типи даних, первинні та зовнішні ключі, обмеження цілісності, індекси та зв’язки між сутностями. Фізична схема БД наведена на діаграмі структури таблиць (див. рис. 2.3), яка демонструє взаємозв’язки між об’єктами та дозволяє спроєктувати ефективні механізми доступу до даних.

Рисунок 2.3 – Схема БД
     Створена модель даних забезпечує узгодженість і повноту інформації, необхідної для реалізації функціональності FreshFridge: моніторингу термінів придатності, аналізу умов зберігання, відстеження динаміки телеметрії та формування сповіщень. Вона також є основою для подальшої реалізації REST API та бізнес-логіки серверної частини.

	2.4 Програмна реалізація серверної частини
     Серверна частина програмної системи FreshFridge реалізована з використанням платформи Node.js та фреймворку Express із застосуванням мови TypeScript. Такий вибір технологій забезпечує модульність, масштабованість та зручність подальшого розвитку системи, а також чітке розмежування відповідальностей між компонентами.
     Архітектура серверної частини побудована за принципом багатошарової моделі, що включає:
- рівень маршрутизації (Routes),
- рівень бізнес-логіки (Services),
- рівень доступу до даних (Repositories),
- рівень валідації та middleware.
     Для зберігання даних використовується реляційна база даних Microsoft SQL Server, підключення до якої здійснюється за допомогою бібліотеки mssql. Взаємодія з БД відбувається через параметризовані SQL-запити, що забезпечує захист від SQL-інʼєкцій та відповідність фізичної схеми БД розробленій ER-діаграмі.
     Для забезпечення безпеки доступу до API реалізовано механізм JWT-автентифікації. Користувачі можуть реєструватися та входити в систему через відповідні HTTP-ендпойнти:
- POST /api/auth/register — реєстрація нового користувача;
- POST /api/auth/login — автентифікація користувача та отримання access token.
     Після успішної автентифікації сервер повертає JWT-токен, який використовується для доступу до захищених ресурсів системи. Перевірка токена здійснюється за допомогою middleware authMiddleware (див. рис. 2.4).
     Нижче наведено фрагмент коду сервісу автентифікації, який відповідає за формування JWT-токена:
       private signAccessToken(id: string, email: string) {
         return jwt.sign(
           { id, email },
           process.env.JWT_ACCESS_SECRET!,
           { expiresIn: process.env.JWT_ACCESS_EXPIRES_IN ?? "15m" }
         );
       }

Рисунок 2.4 – Результат реєстрації користувача через API
     Центральним елементом серверної частини є модуль Products, який реалізує основну бізнес-логіку системи FreshFridge — зберігання та контроль термінів придатності продуктів.
     Модуль підтримує такі операції:
- додавання продукту;
- отримання списку продуктів користувача з підтримкою пагінації;
- отримання продуктів, термін придатності яких наближається до завершення.
     Для кожного запиту реалізовано валідацію вхідних даних за допомогою бібліотеки Zod, що дозволяє відфільтровувати некоректні параметри ще до виконання бізнес-логіки.
     Нижче наведено фрагмент маршруту для додавання нового продукту:
       router.post(
         "/api/products",
         authMiddleware,
         validateBody(createProductSchema),
         async (req, res) => {
           const result = await service.create(req.user!.id, req.body);
           res.status(201).json(result);
         }
       );
     Бізнес-логіка модуля винесена у сервіс ProductsService, який відповідає за перевірку прав доступу та взаємодію з репозиторієм. Безпосередня робота з базою даних здійснюється в класі ProductsRepository (див. рис. 2.5).
     Фрагмент коду запиту для отримання продуктів із бази даних:
       const res = await pool.request()
         .input("user_id", sql.UniqueIdentifier, userId)
         .query(`
           SELECT *
           FROM Products
           WHERE user_id = @user_id
           ORDER BY created_at DESC
         `);
       

Рисунок 2.5 – Отримання списку продуктів користувача
	Для реалізації ключової функції системи — моніторингу свіжості продуктів — реалізовано спеціалізований ендпойнт: GET /api/products/expiring?days=N.
     Цей ендпойнт повертає список активних продуктів користувача, термін придатності яких закінчується протягом заданої кількості днів (див. рис. 2.6). Обчислення виконується безпосередньо на рівні SQL-запиту з використанням функції DATEADD.
     Фрагмент SQL-запиту:
       SELECT *
       FROM Products
       WHERE user_id = @user_id
         AND status = 'active'
         AND expiration_date <= DATEADD(day, @days, CAST(GETDATE() AS date))
       ORDER BY expiration_date ASC

Рисунок 2.6 – Отримання продуктів із наближеним терміном придатності
	Тестування реалізованих API-ендпойнтів виконувалося за допомогою інструменту Thunder Client, що дозволило перевірити коректність HTTP-відповідей, роботу механізму автентифікації та відповідність даних структурі бази даних.
     Усі реалізовані запити повертають коректні HTTP-статуси (200, 201) та відповідають вимогам специфікації API.
     
     
     
     
     
     
     
     
     
     
     
     













ВИСНОВКИ
     У ході виконання лабораторної роботи №2 було спроєктовано та реалізовано серверну частину програмної системи FreshFridge, призначеної для моніторингу свіжості продуктів у холодильнику.
     Серверну частину реалізовано з використанням платформи Node.js, фреймворку Express та мови TypeScript, що дозволило забезпечити модульність архітектури, розмежування бізнес-логіки та зручність подальшого масштабування системи. Для доступу до даних застосовано параметризовані SQL-запити, що підвищує рівень безпеки та захищає систему від SQL-інʼєкцій.
     У рамках лабораторної роботи реалізовано механізм JWT-автентифікації, який забезпечує захищений доступ користувачів до функціоналу системи. Також реалізовано основні API-ендпойнти для управління продуктами, включно з додаванням продуктів, отриманням їх списку та визначенням продуктів із наближеним терміном придатності, що є ключовою бізнес-функцією системи FreshFridge.
     Коректність роботи серверної частини перевірено шляхом тестування HTTP-запитів за допомогою інструменту Thunder Client, що підтвердило відповідність реалізованого API заданій специфікації та правильність обробки даних. Отримані результати свідчать про досягнення мети лабораторної роботи та створення надійної основи для подальшого розвитку системи в межах наступних лабораторних робіт і курсового проєкту.
