1 ЗАВДАННЯ
У ході виконання лабораторної роботи №3 необхідно спроєктувати та реалізувати розширену бізнес-логіку серверної частини програмної системи FreshFridge (моніторинг свіжості продуктів у холодильнику), а також функції адміністрування для керування даними й користувачами системи. Основний акцент роботи — реалізація алгоритмів обробки даних, які виходять за межі стандартних CRUD-операцій, та запровадження механізмів керування доступом і адміністративних операцій. 
У процесі виконання лабораторної роботи необхідно:
* розробити бізнес-логіку серверної частини системи FreshFridge на основі вже спроєктованої БД та API, зокрема алгоритми визначення наближення завершення терміну придатності, формування попереджень і рекомендацій, а також обробку телеметрії IoT-датчиків (температура, вологість, стан дверцят) для оцінювання умов зберігання;
* реалізувати автоматизоване формування подій/сповіщень на основі бізнес-правил; 
* розробити функції адміністрування серверної частини; 
* створити програмну реалізацію бізнес-логіки та адміністративних функцій у вигляді модулів/сервісів серверного застосунку та відповідних API-ендпойнтів.










2 ОПИС ВИКОНАНОЇ РОБОТИ
2.1. Опис інженерних рішень та архітектури системи
Серверна частина програмної системи FreshFridge реалізована з використанням платформи Node.js та фреймворку Express із застосуванням мови програмування TypeScript. Такий підхід дозволяє поєднати високу продуктивність, масштабованість та строгий контроль типів, що зменшує кількість помилок під час розробки.
Архітектура системи побудована за багатошаровим принципом, який передбачає розділення логіки обробки HTTP-запитів, бізнес-логіки та доступу до бази даних. Це забезпечує зрозумілу структуру проєкту, спрощує супровід коду та дозволяє незалежно розширювати окремі функціональні модулі.
Для зберігання даних використовується система керування базами даних Microsoft SQL Server. Взаємодія з базою даних реалізована через явні SQL-запити без використання ORM, що забезпечує повний контроль над структурою таблиць, індексами та тригерами. У базі даних реалізовано логічне видалення записів, автоматичне оновлення часових міток та оптимізацію запитів за допомогою індексів.
Безпека серверної частини забезпечується використанням JWT-автентифікації та рольової моделі доступу. Реалізовано окремий функціонал адміністрування, який дозволяє керувати ролями користувачів, блокувати облікові записи та вести журнал адміністративних дій. Для обробки складних бізнес-процесів використовується механізм фонових задач, зокрема для аналізу термінів придатності продуктів і формування сповіщень.
Реалізована архітектура забезпечує готовність серверної частини до подальшого розширення, зокрема інтеграції з IoT-пристроями та розробки клієнтських застосунків.
2.2. Моделювання поведінки системи
Після реалізації базових CRUD-операцій у системі FreshFridge важливо показати бізнес-логіку, яка спрацьовує під час додавання продукту: перевірку коректності введених даних, розрахунок дати придатності, присвоєння статусу свіжості та (за потреби) створення сповіщення. Для цього доцільно використати діаграму діяльності, оскільки вона наочно демонструє послідовність кроків і розгалуження за умовами.
Покроковий опис діаграми (див. рис. 2.1):
1. Користувач ініціює дію «Додати продукт» у клієнтському застосунку.
2. Клієнт відображає форму введення даних продукту (назва, категорія, кількість, дата придбання, або “вжити до”, або “термін у днях”, а також холодильник/полиця).
3. Користувач натискає «Зберегти», клієнт надсилає запит на сервер.
4. Сервер виконує валідацію даних (обов’язкові поля, коректність дат, коректність числових значень).
5. Сервер перевіряє існування і доступ до цільового холодильника/полиці (щоб не можна було додати продукт “на чужу полицю”).
6. Якщо будь-яка перевірка неуспішна — сервер повертає помилку, клієнт показує повідомлення, процес завершується.
7. Якщо перевірки успішні — сервер визначає expiryDate: якщо передано useByDate — береться як є; інакше, якщо передано shelfLifeDays — expiryDate = purchaseDate + shelfLifeDays.
8. Сервер виконує оцінку свіжості: обчислює кількість днів до завершення (daysLeft) та визначає статус (наприклад: FRESH, EXPIRING_SOON, EXPIRED) відповідно до правил системи.
9. Сервер зберігає продукт у БД і (за потреби) фіксує службову подію/історію (audit).
10. Якщо статус EXPIRING_SOON або EXPIRED — сервер створює сповіщення для користувача.
11. Сервер повертає успішну відповідь з розрахованими полями (expiryDate, status, daysLeft), клієнт оновлює список продуктів.
  

Рисунок 2.1 – Діаграма діяльності «Додавання продукту та первинна оцінка свіжості»
        Зафіксуємо алгоритм обробки телеметрії як бізнес-процес: від прийому показників до прийняття рішення про ризик псування та створення попередження. UML-діаграма діяльності дозволяє чітко відобразити перевірки, розгалуження та антиспам-умову, не прив’язуючись до конкретної реалізації.
Покроковий опис діаграми (див. рис. 2.2):
1. IoT-модуль (або симулятор) надсилає пакет телеметрії на сервер (температура, вологість, стан дверцят, час, deviceId).
2. Сервер приймає запит і виконує перевірку автентичності пристрою (ключ/токен).
3. Якщо пристрій неавторизований — обробка завершується помилкою доступу.
4. Якщо автентифікація успішна — сервер виконує валідацію даних (формат, допустимі діапазони значень).
5. Якщо дані некоректні — повертається помилка валідації, обробка завершується.
6. Якщо дані коректні — телеметрія зберігається в БД для подальшої аналітики (графіки/історія).
7. Система визначає порогові значення для порівняння (глобальні або прив’язані до конкретного холодильника/зони).
8. Виконується аналіз умов зберігання: перевірка: температура в нормі?; перевірка: вологість в нормі?; додаткова перевірка: дверцята не були відкриті занадто довго/часто.
9. Якщо порушень немає — система повертає успіх без створення попереджень.
10.  Якщо порушення є — система формує подію ризику та перевіряє антиспам-умову: чи не було такого ж попередження нещодавно.
11.  Якщо антиспам не дозволяє — сповіщення не створюється (лише фіксується факт порушення в історії).
12.  Якщо антиспам дозволяє — створюється сповіщення та (опційно) запис у журналі подій.
13.  Сервер повертає відповідь IoT-модулю про успішний прийом даних.
  

Рисунок 2.2 – UML-діаграма діяльності «Обробка телеметрії та оцінка умов зберігання»
Ключовою є логіка, яка працює без прямої дії користувача: система має регулярно перевіряти терміни придатності та створювати сповіщення про продукти, що скоро зіпсуються або вже прострочені. Таку взаємодію зручно показати діаграмою послідовності, оскільки вона відображає обмін повідомленнями між планувальником задач, сервісами бізнес-логіки та базою даних.
Покроковий опис діаграми (див. рис. 2.3):
1. Планувальник (cron/внутрішній scheduler) запускає задачу «Перевірка свіжості продуктів» за розкладом (наприклад, щогодини або раз на добу).
2. Задача викликає Сервіс перевірки свіжості.
3. Сервіс запитує у БД список активних продуктів (не видалених/не архівованих) з полями, потрібними для розрахунку: expiryDate, userId, status тощо.
4. Для кожного продукту сервіс: обчислює днів_залишилось до завершення терміну; визначає новий статус (СВІЖИЙ, СКОРО ЗІПСУЄТЬСЯ, ПРОСТРОЧЕНИЙ).
5. Якщо статус змінився — сервіс оновлює продукт у БД (щоб клієнт бачив актуальний стан).
________________
6. Якщо продукт переходить у стан СКОРО ЗІПСУЄТЬСЯ або ПРОСТРОЧЕНИЙ — сервіс перевіряє, чи не було вже створено дублююче сповіщення за останній період (антиспам-логіка).
7. Якщо дублю немає — створюється запис Сповіщення у БД.
8. Після цього Сервіс доставки сповіщень надсилає push/in-app повідомлення користувачу.
9. Задача завершується, планувальник очікує наступного запуску.
  

Рисунок 2.3 – Діаграма послідовності «Періодична перевірка продуктів і генерація сповіщень»
Окрім контролю термінів придатності, система FreshFridge повинна враховувати умови зберігання (температура, вологість, стан дверцят). Дані надходять від IoT-модуля/симульованих сенсорів і мають бути збережені, проаналізовані та, у разі виходу параметрів за допустимі межі, спричинити створення попередження для користувача. Таку взаємодію найкраще відобразити діаграмою послідовності, оскільки вона показує шлях повідомлення: від сенсора → до API → БД → модуля аналізу → сповіщень.
Покроковий опис діаграми (див. рис. 2.4):
   1. IoT-модуль (або симулятор) формує пакет телеметрії (температура, вологість, стан дверцят, час вимірювання, ідентифікатор пристрою).
   2. IoT-модуль надсилає запит на сервер: POST /telemetry.
   3. Сервер API виконує первинну перевірку: формат даних, коректність значень, автентифікація пристрою (токен/ключ).
   4. Сервер зберігає телеметрію в БД (історія вимірювань потрібна для графіків та аудиту).
   5. Сервер передає дані в Сервіс аналізу умов зберігання, який: порівнює значення з допустимими порогами (окремо для температури/вологості); враховує стан дверцят (наприклад, якщо дверцята відкриті довго — ризик підвищується).
   6. Якщо пороги не порушені — система завершує обробку (лише логування/зберігання).
   7. Якщо порушення є — сервіс формує подію “ризик псування” і перевіряє антиспам-умову (щоб не створювати десятки однакових попереджень).
   8. Якщо антиспам дозволяє — створюється сповіщення в БД.
   9. Сервіс сповіщень надсилає push/in-app повідомлення користувачу.
   10.  Сервер повертає IoT-модулю успішну відповідь про прийом телеметрії.
  

Рисунок 2.4 – Діаграма послідовності «Обробка телеметрії IoT та формування попередження про ризик псування»
Важливо мати не лише бізнес-логіку моніторингу, а й адміністративні функції, які забезпечують контроль доступу та безпечну експлуатацію системи. Один із типових адміністративних сценаріїв — блокування користувача. Діаграма послідовності демонструє, як запит адміністратора проходить через перевірку ролей, зміну стану користувача в БД, інвалідацію активних сесій (токенів) та фіксацію події в журналі.
Покроковий опис діаграми (див. рис. 2.5):
   1. Адміністратор відкриває панель адміністрування та обирає користувача зі списку.
   2. Адміністратор ініціює дію «Заблокувати користувача».
   3. Клієнт (адмін-інтерфейс) надсилає на сервер запит PUT /admin/users/{id}/block.
   4. Сервер перевіряє: валідність JWT адміністратора; наявність ролі ADMIN / відповідних прав.
   5. Якщо прав недостатньо — повертається помилка доступу, процес завершується.
   6. Якщо права підтверджені — сервер оновлює користувача в БД (наприклад isBlocked = true, blockedAt, blockedReason).
   7. Далі сервер ініціює відкликання активних токенів користувача (у системі це може бути таблиця сесій/refresh-токенів або список відкликаних токенів).
   8. Сервер створює запис у журналі адміністративних дій (audit log).
   9. Сервер повертає відповідь про успішне блокування.
   10.  Адмін-інтерфейс оновлює список користувачів, відображаючи статус “Заблокований”.
  

Рисунок 2.5 – Діаграма послідовності «Адміністрування: блокування користувача та відкликання доступу»
2.3. Програмна реалізація бізнес-логіки
Для реалізації бізнес-логіки керування продуктами використовується сервісний шар, який відповідає за перевірки коректності даних, взаємодію з репозиторіями та формування результатів для клієнта. Нижче наведено фрагмент реалізації сервісу продуктів:

            export class ProductsService {
  private repo = new ProductsRepository();


  async create(userId: string, dto: CreateProductDto) {
    return this.repo.create(userId, dto);
  }


  async list(userId: string, query: ProductsQuery) {
    return this.repo.list(userId, query);
  }


  async getById(userId: string, id: string) {
    const product = await this.repo.findById(id);
    if (!product || product.user_id !== userId) {
      throw new Error("Product not found");
    }
    return product;
  }


  async update(userId: string, id: string, patch: UpdateProductDto) {
    await this.getById(userId, id);
    return this.repo.update(id, patch);
  }


  async remove(userId: string, id: string) {
    await this.getById(userId, id);
    await this.repo.softDelete(id);
  }
}

        Для автоматизації бізнес-процесів реалізовано фонове завдання перевірки терміну придатності продуктів. Воно аналізує дату закінчення строку зберігання та створює відповідні сповіщення користувачам:


export async function runFreshnessJob() {
  const products = await repo.getExpiringProducts();


  for (const product of products) {
    await notificationsRepo.create({
      user_id: product.user_id,
      type: "EXPIRING",
      title: "Product expiring soon",
      message: `Product ${product.name} is expiring soon`
    });
  }
}


Таким чином, бізнес-логіка серверної частини охоплює керування продуктами, холодильниками, полицями, сповіщеннями, а також автоматичну обробку подій, що забезпечує цілісну роботу програмної системи.
2.4. Програмна реалізація адміністрування серверної частини
Адміністрування серверної частини реалізоване у вигляді окремого модуля з рольовим контролем доступу. Для цього використовується middleware requireRole, який перевіряє наявність у користувача адміністративних прав:
export const requireRole = (role: "admin") => {
  return (req, res, next) => {
    if (req.user?.role !== role) {
      return res.status(403).json({ error: "Forbidden" });
    }
    next();
  };
};


Маршрути адміністрування згруповані в окремому модулі та дозволяють виконувати керування користувачами, системними налаштуваннями та перегляд журналу аудиту:
router.get("/api/admin/users", authMiddleware, requireRole("admin"), async (req, res) => {
  const users = await service.listUsers(req.query);
  res.json(users);
});


router.patch("/api/admin/users/:id/role", authMiddleware, requireRole("admin"), async (req, res) => {
  await service.updateUserRole(req.params.id, req.body.role);
  res.sendStatus(204);
});


Усі адміністративні дії фіксуються у таблиці журналу аудиту, що забезпечує контроль і прозорість змін у системі:
async logAction(adminId: string, action: string, targetUserId?: string, details?: string) {
  await this.db.query(`
    INSERT INTO AdminAuditLog (admin_user_id, action, target_user_id, details)
    VALUES (@adminId, @action, @targetUserId, @details)
  `);
}


Таким чином, серверна частина системи містить повноцінний механізм адміністрування з контролем доступу, журналюванням дій та керуванням системними параметрами, що відповідає вимогам безпеки та масштабованості.
























ВИСНОВКИ
У межах лабораторної роботи №3 було розроблено серверну частину програмної системи FreshFridge, призначеної для обліку продуктів харчування, контролю термінів їх придатності та автоматичного формування сповіщень для користувачів. Серверна частина забезпечує централізоване зберігання даних, обробку запитів клієнтських застосунків та виконання фонових бізнес-процесів.
Під час виконання роботи було спроєктовано структуру бази даних, реалізовано REST API для керування користувачами, холодильниками, полицями, продуктами та сповіщеннями, а також впроваджено механізми автентифікації, авторизації та адміністрування. Окрему увагу приділено реалізації фонових задач для аналізу термінів придатності продуктів і підготовці серверної частини до інтеграції з IoT-пристроями. Для зручності тестування та демонстрації функціоналу реалізовано автоматичну документацію API за допомогою Swagger.
